# Project IVY — Integrations & Hosting Research

## Executive Summary

Project IVY is a multi-tenant, serverless support bot that runs a four-layer escalation ladder (Lex → KB → LLM → ticket) across customer collaboration channels, ITSM systems, knowledge repositories, and intranets. This document consolidates integration research across five categories plus a hosting/portability strategy, with an explicit bot-API verdict per vendor and a phased build order justified by market coverage × integration feasibility.

**Headline recommendations:**

| Category | v1 headline recommendation |
|---|---|
| **Collaboration platforms** (front end) | **Slack + Microsoft Teams** — the two analyst leaders, together covering the overwhelming majority of SMB, mid-market, and enterprise/regulated buyers. Slack is IVY's native surface (lowest effort); Teams unlocks enterprise/regulated. |
| **ITSM systems** (system of record + learning loop) | **Freshservice + Jira Service Management + ServiceNow** — mid-market default, dev-centric co-leader, and the enterprise-gating incumbent. All expose resolved-ticket retrieval for the learning loop. |
| **Internal knowledge** (L2/L3 grounding) | **SharePoint/OneDrive (Graph) + Confluence Cloud + Google Drive/Workspace** — the three cover most IT/HR docs and each supports an ACL-respecting access model. |
| **Intranet / EX** | **Microsoft Viva + Workvivo (Zoom) + Staffbase** — widest M365 reach, a native chatbot-with-webhooks fit, and clean News/Pages APIs for frontline comms. |
| **Hosting** | **Host on AWS now**; make secretless connect-out (Entra WIF, GCP WIF) a v1 requirement; build a thin portability abstraction (data, messaging, LLM, OCR) and move L1 intent onto the LLM to shed the biggest lock-in. Offer Azure/GCP-native deployment as an enterprise SKU. |

A key enabling fact across the whole strategy: Claude — IVY's default L3 LLM — is available first-party on all three hyperclouds (Bedrock, Vertex AI, Azure/Microsoft Foundry), so the LLM layer does not lock IVY to any one cloud. Critically for regulated buyers, Claude on Vertex AI is now FedRAMP High and DoD IL2 authorized, so all three clouds clear the federal LLM bar for IVY's specific model.

All four candidates expose a bot/app API capable of the core receive-reply-interact loop; they differ in ecosystem maturity, auth model, and default customer segment.

**One codebase, multiple platforms:** realistic but not free. Each platform has a distinct event schema, auth model, and card grammar (Block Kit JSON vs Adaptive Cards vs Google Chat cards vs Zoom message JSON). The practical pattern is a shared IVY core behind per-platform adapters that normalize inbound events and translate a canonical message/card model outward — proven in production (e.g., Vercel's Chat SDK unifies Slack, Teams, Google Chat behind one event-driven interface) [[21]](https://github.com/vercel/chat) [[22]](https://vercel.com/blog/chat-sdk-brings-agents-to-your-users). Expect the interactive/card layer to need the most per-platform code.

**Flags:** Market-share figures (Slack ~18.6%/~79M DAU, Teams ~37%/~320M MAU, Google Chat ~100 apps) come from vendor-adjacent/aggregator sites, not a single audited source, and "market share" is defined inconsistently — treat as directional only. Teams' 10–15s bot-response timeout and inconsistent Adaptive-Card thread correlation are real friction points for IVY's async LLM/OCR latency design. Zoom's PARTIAL is a judgment on interactive depth/ecosystem, not raw capability.

## 3. Internal Knowledge Sources (L2/L3 Grounding)

Repositories IVY must read to ground answers. The core question per vendor: can IVY programmatically search/fetch content *and* does the API preserve per-user access controls (ACLs) so IVY never surfaces a document the asking user cannot already see? Microsoft and Google offer permission-trimmed enterprise search out of the box; the rest require IVY to model ACLs itself or accept an integration-scoped view.

| Vendor | Segment fit | Bot API? | Auth | Read/Write | Events/Webhooks | Effort | v1? |
|---|---|---|---|---|---|---|---|
| **SharePoint / OneDrive** (Graph) | SMB · Mid · Ent | **YES** | Entra ID OAuth 2.0; delegated (per-user trim) or app + admin consent; `Sites.Selected` scoping | Read + Write | Yes (Graph change notifications) | Med | **Yes** |
| **Confluence Cloud** | SMB · Mid · Ent | **YES** | OAuth 2.0 (3LO) / Forge; granular read scopes | Read + Write | Yes (Connect webhooks, best-effort) | Med | **Yes** |
| **Google Drive / Workspace** | SMB · Mid · Ent | **YES** | OAuth 2.0 per-user, or service account + domain-wide delegation | Read + Write | Yes (Drive `changes.watch` push) | Med | **Yes** |
| **Slack message history** | SMB · Mid; Ent (Grid for full history) | **PARTIAL** | Bot token (`xoxb`) for channel history; user token (`xoxp`) for search; Discovery API org-wide | Read (+ write elsewhere) | Yes (Events API `message.*`) | Med–High | **Partial (v1.5)** |
| **Notion** | SMB · Mid | **PARTIAL** | OAuth 2.0 integration; capability-scoped | Read + Write | Yes (page/DB events) | Low | **Defer** |
| **Microsoft Teams message history** | Mid · Ent | **PARTIAL** | Graph app permissions; **protected API** (extra approval) | Read (export) + Write | Yes (change notifications) | High | **Defer** |

**Vendor detail:**

- **SharePoint/OneDrive (Graph) — YES.** Microsoft Search API (`POST /search/query`) searches `driveItem`, `listItem`, `site`, `externalItem`; results are scoped to enforce item access control, giving built-in per-user ACL trimming with delegated permissions ([Search API overview](https://learn.microsoft.com/en-us/graph/api/resources/search-api-overview?view=graph-rest-1.0); [Permissions overview](https://learn.microsoft.com/en-us/graph/permissions-overview)). App-mode needs admin consent ([Grant admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)). `Sites.Selected` restricts to named sites in both modes ([Sites.Selected](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)). **Caveat:** `/search/query` does *not* work with `Sites.Selected` alone — it needs `Files.Read.All`/`Sites.Read.All` ([Sites.Read.All](https://graphpermissions.merill.net/permission/Sites.Read.All)), so granular scoping and unified search partly conflict.
- **Confluence Cloud — YES.** OAuth 2.0 (3LO) with granular read scopes ([scopes](https://developer.atlassian.com/cloud/confluence/scopes-for-oauth-2-3LO-and-forge-apps/)). **Flag:** CQL search lives only in v1 REST (`/wiki/rest/api/search`); typical integration uses v2 for read/write + v1 for search ([v2 intro](https://developer.atlassian.com/cloud/confluence/rest/v2/intro/)). Webhook delivery is best-effort ([webhooks](https://developer.atlassian.com/cloud/confluence/using-webhooks/)). 3LO runs as the user, so results respect that user's permissions.
- **Google Drive/Workspace — YES.** Drive API v3 `files.list` supports full-text search; per-user OAuth 2.0, or service account + domain-wide delegation for tenant-wide access ([DWD](https://support.google.com/a/answer/162106?hl=en); [scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)). For unified ACL-trimmed enterprise search across Drive + third-party repos, Google Cloud Search runs permission-filtered queries ([Map ACLs](https://developers.google.com/workspace/cloud-search/docs/guides/acls)). **Flag:** Cloud Search third-party indexing requires ≥500 licenses + a certified partner ([Index third-party data](https://support.google.com/a/answer/11180370?hl=en)) — for SMB use Drive API directly; reserve Cloud Search for enterprise.
- **Slack message history — PARTIAL.** `conversations.history` reads channels with a bot token, but the bot must be invited to each channel ([conversations.history](https://docs.slack.dev/reference/methods/conversations.history/)). `search.messages` does **not** work with bot tokens — needs a user token (`xoxp`) with `search:read` ([scopes](https://api.slack.com/scopes)). Org-wide history is only via the Discovery API (Enterprise Grid–only, sanctioned for security/compliance, not grounding) ([Discovery guide](https://slack.com/help/articles/360002079527-A-guide-to-Slacks-Discovery-APIs)).
- **Notion — PARTIAL.** `POST /v1/search` returns only content explicitly shared with the integration ([API connections](https://www.notion.com/help/create-integrations-with-the-notion-api)); webhooks exist ([webhooks](https://developers.notion.com/reference/webhooks-events-delivery)). Flat integration-level view, not per-user ACLs.
- **Microsoft Teams message history — PARTIAL.** Retrievable via Graph + Export API (`getAllMessages`), but these are **protected APIs** requiring extra Microsoft approval ([Export Teams content](https://learn.microsoft.com/en-us/microsoftteams/export-teams-content)). Since **Aug 25, 2025** these metered Graph APIs are no longer metered ([payment models](https://learn.microsoft.com/en-us/graph/teams-licenses); [metered list](https://learn.microsoft.com/en-us/graph/metered-api-list)). Still high effort (approval gate + no native per-user search trimming).

## 5. Console Build Plan

Build order is justified by **market coverage × integration feasibility**: front the two dominant collaboration surfaces first (they gate every deal), pair them with the ITSM and knowledge connectors that cover the mid-market and enterprise, and layer intranet reach on top. Build the per-platform adapter abstraction in v1 so later additions do not force re-architecture.

### v1 shortlist (with counts)

| Category | v1 count | v1 vendors |
|---|---|---|
| Collaboration platforms | **2** | Slack, Microsoft Teams |
| ITSM systems | **3** | Freshservice, Jira Service Management, ServiceNow |
| Internal knowledge | **3** | SharePoint/OneDrive (Graph), Confluence Cloud, Google Drive/Workspace |
| Intranet / EX | **3** | Microsoft Viva, Workvivo (Zoom), Staffbase |
| **v1 total** | **11 connectors** | |

### Phased build order

**v1 — Core coverage (highest reach × lowest/known effort):**
- **Collaboration:** Slack (native, lowest effort) → Microsoft Teams (unlocks enterprise/regulated). Ship the canonical event/card adapter layer now.
- **ITSM:** Freshservice (mid-market default, lowest effort) → Jira Service Management (dev-centric mid-market, modern OAuth + Dynamic Webhooks) → ServiceNow (high effort, non-negotiable for enterprise; ship the customer-side Business Rule template for eventing).
- **Knowledge:** SharePoint/OneDrive, Confluence Cloud, Google Drive/Workspace — all three respect source ACLs, essential for governed multi-tenant retrieval.
- **Intranet:** Microsoft Viva, Workvivo, Staffbase.

**v2 — Fast-follows (strong coverage, one verification/effort caveat each):**
- **Collaboration:** Google Chat (Workspace-standardized mid-market).
- **ITSM:** Zendesk (SMB/support-led, easy API — build OAuth from day one) and ManageEngine ServiceDesk Plus (mid-market value tier, two auth paths).
- **Knowledge (v1.5):** Slack message history, Notion, Teams message history — each strong but carries a permission/approval caveat.
- **Intranet:** Simpplr, LumApps (both Gartner + Forrester Leaders) once webhook behavior is confirmed.

**v3 — Long tail (lower per-connector deal value or gated APIs):**
- **Collaboration:** Zoom Team Chat (low demand).
- **ITSM:** SolarWinds Service Desk and the SMB helpdesk cluster (Zoho Desk, Freshdesk, HaloITSM, Spiceworks) — high fan-out for lower deal value.

## 6. Hosting & Portability

Two horizons: **NOW** (stay on AWS, connect out to Microsoft and Google) and **LATER** (run the same backend natively on Azure/GCP for customers who mandate their own cloud). Enabling fact: Claude is available first-party on all three hyperclouds with same-day launches through 2026, so the LLM layer does not lock IVY to any cloud ([Anthropic/Amazon](https://www.anthropic.com/news/anthropic-amazon-compute), [Claude on Vertex](https://platform.claude.com/docs/en/build-with-claude/claude-on-vertex-ai), [Claude multi-cloud](https://www.digitalapplied.com/blog/claude-code-auto-mode-bedrock-vertex-foundry-2026)).

### (a) NOW — AWS backend + connect-out

IVY runs in your AWS account and reaches into each customer's M365/Entra and Google Workspace tenant. A classic multi-tenant SaaS "connect-out" pattern.

| Ecosystem | Auth model | Consent/onboarding | Secretless option | Verdict |
|---|---|---|---|---|
| **Microsoft (Entra/Graph)** | One **multi-tenant app**; OAuth 2.0 **client-credentials** (app perms) for background reads + **delegated** for on-behalf-of actions | Customer global admin grants **tenant-wide admin consent** via admin-consent URL | **YES** — Lambda uses **Entra Workload Identity Federation** (via Cognito/OIDC); no stored per-tenant secret | **YES** |
| **Google (Workspace)** | OAuth 2.0; prefer **Marketplace app install** or **per-user consent**; **DWD** only for unattended cross-user reads | Admin installs Marketplace app or authorizes service-account client ID | **YES** — AWS uses **GCP Workload Identity Federation** (STS `GetCallerIdentity`); no SA keys at rest | **PARTIAL** |

**Microsoft details.** App permissions in client-credentials *always* require admin consent, and you must use the tenant-specific token endpoint, not `/common/` ([app access to web APIs](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-configure-app-access-web-apis), [Aembit](https://aembit.io/blog/authenticate-to-microsoft-graph-api-using-oauth-2-0-client-credentials/)). Convert to multi-tenant for self-onboarding ([convert to multitenant](https://learn.microsoft.com/en-us/entra/identity-platform/howto-convert-app-to-be-multi-tenant), [admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)). Strongest posture: no per-tenant secrets via Entra WIF ([WIF overview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation), [Graph via WIF + Cognito](https://dev.to/samconibear/no-certs-no-secrets-microsoft-graph-on-azure-using-entra-workload-identity-federation-and-amazon-18c9)).

**Flag (corrected):** Microsoft is tightening app-identity rules — **service-principal-less authentication is blocked as of March 31, 2026** (per Microsoft's retirement notice), *not* April 1, 2026 as the draft stated. The substance is unchanged: every tenant must provision a service principal. Reference the dedicated retirement doc ([retire service-principal-less authentication](https://learn.microsoft.com/en-us/entra/identity-platform/retire-service-principal-less-authentication)), not the generic Workload Identities overview.

**Google — why PARTIAL.** Access works, but the low-friction unattended path (DWD) is being discouraged and fenced: Google recommends avoiding DWD in favor of OAuth consent or Marketplace apps; high-privilege DWD can require multi-party (second super-admin) approval (since Aug 2024); restricted Gmail scopes require annual **CASA Tier 2** ([Unipile DWD guide](https://www.unipile.com/gmail-api-service-account-domain-wide-delegation/), [Google DWD best practices](https://knowledge.workspace.google.com/admin/apps/domain-wide-delegation-best-practices), [Workspace API verification](https://singhamandeep.com/google-workspace-api-verification-guide/)). Recommended: ship a **Workspace Marketplace app** ([configure OAuth consent](https://developers.google.com/workspace/marketplace/configure-oauth-consent-screen), [control API access](https://support.google.com/a/answer/13152743?hl=en)). PARTIAL because production onboarding requires Google's verification/CASA process and admin cooperation.

**Net for NOW:** Staying on AWS is the right default. Both connect-outs are achievable **without storing customer secrets** (Entra WIF; GCP WIF) — the single most important design decision for security posture and enterprise sales.

### (b) LATER — Multi-cloud portability (native Azure/GCP)

| AWS component | Azure | GCP | Effort | Notes/risk |
|---|---|---|---|---|
| **Lambda** | Azure Functions | Cloud Run (functions) | **Medium** | Handler/trigger models differ; containerize to maximize portability ([serverless 2026](https://reintech.io/blog/aws-lambda-vs-azure-functions-vs-google-cloud-functions-serverless-comparison-2026), [Lambda vs Cloud Run vs Functions](https://devopsboys.com/blog/aws-lambda-vs-google-cloud-run-vs-azure-functions-2026)) |
| **SQS** | Service Bus | Pub/Sub | **Low–Medium** | Delivery semantics differ ([messaging comparison](https://www.hakia.com/posts/comparing-major-serverless-providers-aws-azure-and-google-cloud)) |
| **DynamoDB** | Cosmos DB | Firestore | **High** | Single-table + GSIs don't map cleanly — **one of the hardest to replace** ([NoSQL comparison](https://www.pluralsight.com/resources/blog/cloud/comparing-cloud-nosql-databases-dynamodb-vs-cosmos-db-vs-cloud-datastore-and-bigtable), [db-engines](https://db-engines.com/en/system/Amazon+DynamoDB%3BGoogle+Cloud+Firestore%3BMicrosoft+Azure+Cosmos+DB)) |
| **Bedrock** (L3 LLM) | Azure AI Foundry / Azure OpenAI | Vertex AI | **Low** | Claude on all three; wrap behind a provider-agnostic client ([platform comparison](https://www.index.dev/skill-vs-skill/ai-aws-bedrock-vs-azure-ai-vs-vertex), [Bits Lovers](https://www.bitslovers.com/bedrock-vs-azure-ai-foundry-vs-vertex-ai/)) |
| **Lex** (L1 intent) | Azure CLU + Bot Service | Dialogflow CX | **High** | Proprietary models, no portable export — **hardest besides DynamoDB** ([Lex alternatives](https://dasha.ai/tips/amazon-lex-alternatives), [Lex vs Dialogflow](https://www.happyfox.com/compare/google-dialogflow-vs-amazon-lex/)) |
| **Textract** (OCR) | Azure Document Intelligence | Google Document AI | **Medium** | Schemas differ; needs an adapter. Accuracy roughly comparable — **benchmark figures vary by document type, treat as indicative** ([OCR comparison](https://soceton.com/blogs/aws-textract-vs-google-document-ai-vs-azure-document-intelligence), [imagetotable](https://imagetotable.ai/blog/google-vs-aws-vs-azure-ocr-2026)) |
| **Step Functions / EventBridge** | Durable Functions / Event Grid | Workflows / Eventarc | **High** | Deep proprietary orchestration is expensive to port; keep glue thin |

**Hardest-to-replace (rank):** (1) DynamoDB access patterns/single-table design; (2) Lex intent models (no portable format); (3) proprietary orchestration glue. Bedrock and messaging are easiest to abstract.

**Strategic mitigation:** Since IVY already has a vendor-agnostic LLM, consider **collapsing L1 intent matching into the LLM** rather than deepening Lex/Dialogflow reliance — removing the highest-lock-in NLU component and making the whole ladder cloud-portable ([Lex 2026 guide](https://www.signisys.com/blog/amazon-lex-the-complete-guide-to-aws-conversational-ai/)). **Recommended play:** containerize compute (Cloud Run / container-based Functions), keep an abstraction over data/messaging/LLM/OCR, and treat OCR + intent as pluggable adapters.

### (c) Data-residency, security & compliance by segment

All three hyperscalers hold core certs (SOC 2, ISO 27001), sign **HIPAA BAAs** for eligible services, support GDPR, and offer EU data-residency/sovereign options — so the *cloud* rarely blocks a deal; **IVY's own compliance posture is what customers audit.** SOC 2 is now baseline, routinely demanded before signing ([SOC 2 baseline](https://www.secureleap.tech/blog/soc-2-compliance-checklist-saas), [SaaS checklist](https://zylo.com/blog/saas-compliance-checklist)).

| Segment | Table-stakes | Data residency | 2026 driver |
|---|---|---|---|
| **SMB (<100)** | SOC 2 Type II; encryption + MFA; Trust page | Single region usually fine | HIPAA if healthcare — 2026 Security Rule overhaul mandates encryption, MFA, segmentation, annual pen-testing, 72-hr recovery ([SMB checklist](https://afocalsolutions.com/blog/2026-04-27-smb-compliance-checklist-2026-soc-2-hipaa-and-cmmc-requireme/), [HIPAA 2026](https://www.strac.io/blog/soc-2-compliance-software)) |
| **Mid-market (100–2000)** | SOC 2 Type II **+ ISO 27001**; vendor-risk/DPA reviews | Regional (EU/US) commitments common | ISO 27001 for global expansion ([frameworks by size](https://www.strac.io/blog/soc-2-compliance-software)) |
| **Enterprise (2000+)** | SOC 2 + ISO 27001 + often HIPAA/FedRAMP/CMMC; IR plan, pen tests, sub-processor transparency | **Sovereign/in-region often mandatory**; customer-managed keys | Regulated & EU/public-sector buyers drive sovereign clouds ([IR requirement](https://www.saasfourm.com/navigating-saas-compliance-and-data-privacy/)) |

**Sovereign options (enterprise LATER lever), all live in 2026:**
- **AWS European Sovereign Cloud** — launched **Jan 15, 2026** (Brandenburg, Germany); separate partition, EU-resident operators, EU-held keys/root CA ([Towards The Cloud](https://towardsthecloud.com/blog/aws-european-sovereign-cloud), [factualminds](https://www.factualminds.com/blog/aws-data-residency-sovereignty-guide-2026/)).
- **Microsoft EU Data Boundary + M365 Local / Foundry Local** (Feb 2026) — AI inference on customer hardware, disconnected from public cloud ([Two Sovereign Clouds](https://julsimon.medium.com/two-sovereign-clouds-one-legal-wall-ff39bcc0432b), [TechCrunch](https://techcrunch.com/2025/02/26/microsoft-finalizes-its-eu-sovereign-cloud-project/)).
- **Google sovereign** — data-trustee models: T-Systems (Germany), S3NS/Thales (France, pursuing SecNumCloud) ([overview](https://julsimon.medium.com/two-sovereign-clouds-one-legal-wall-ff39bcc0432b)).

**FedRAMP for US federal — all three clouds clear the bar for IVY (corrected):** Claude in Amazon Bedrock is authorized for FedRAMP High (and DoD IL4/5); Azure OpenAI holds FedRAMP High. **The earlier "Vertex in progress" caveat is now outdated:** Generative AI on Vertex AI (the Gemini-hosting platform) achieved FedRAMP High authorization in 2025 ([Google Cloud blog](https://cloud.google.com/blog/topics/public-sector/vertex-ai-search-and-generative-ai-with-gemini-achieve-fedramp-high)), and — decisively for IVY, whose default L3 model is Claude — **Claude on Google Cloud's Vertex AI is explicitly authorized for FedRAMP High and DoD IL2** ([Anthropic](https://www.anthropic.com/news/claude-on-google-cloud-fedramp-high), [Claude](https://claude.com/blog/claude-on-google-cloud-fedramp-high)). The exact federal LLM workload the draft worried about is therefore covered on Vertex today. On the FedRAMP-High dimension GCP/Vertex is now at parity with Bedrock and Azure OpenAI, not behind them. (Bedrock's Claude reaches higher DoD impact levels — IL4/5 vs Vertex's IL2 — which still matters for classified-adjacent defense work; verify the specific impact level and ATO scope at contract time.)

### Segment-fit summary & hosting verdicts

| Vendor / target | SMB | Mid | Enterprise | Verdict |
|---|---|---|---|---|
| **AWS (host NOW)** | Fit | Fit | Fit | **YES** — default backend home |
| **Microsoft Graph/Entra (connect-out)** | Fit | Fit | Strong | **YES** — multi-tenant app + admin consent + WIF; no secrets |
| **Google Workspace (connect-out)** | Fit | Fit | Fit w/ effort | **PARTIAL** — Marketplace app + CASA/verification; DWD restricted |
| **Azure/Foundry (host LATER)** | Overkill | Fit | Strong (MS-first, sovereign) | **YES** — natural for MS-centric & EU-sovereign |
| **GCP/Vertex (host LATER)** | Overkill | Fit | Fit (incl. FedRAMP-High federal) | **YES** — Claude on Vertex is FedRAMP High + IL2; porting cost (DynamoDB/Lex) is the real constraint, not compliance |

*Note:* GCP's hosting verdict is upgraded from PARTIAL to **YES** — the prior downgrade rested solely on a now-resolved FedRAMP caveat. The Google *connect-out* (row 3) remains PARTIAL for an unrelated reason: Workspace DWD/CASA onboarding friction, not FedRAMP.

**Bottom line:** Host on **AWS now**; make secretless connect-out (Entra WIF, GCP WIF) a v1 requirement. Build a thin portability abstraction over data, messaging, LLM, and OCR, and move L1 intent onto the LLM to shed the biggest lock-in. Offer Azure/GCP-native deployment as an enterprise SKU, priced for the DynamoDB, Lex, and orchestration porting cost — the compliance story on all three clouds (including GCP/Vertex FedRAMP High for Claude) is no longer a differentiator between them.

*Caveats: OCR accuracy percentages and cost-gap claims in vendor blogs vary by workload — validate on IVY's own samples; specific FedRAMP impact levels (e.g., Vertex IL2 vs Bedrock IL4/5) and sovereign-cloud statuses change — re-verify ATO scope at contract time.*
