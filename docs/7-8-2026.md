3. Karan's Questions & Manoj Answers
   Q1: When connecting to Slack, does the flow ask for a specific channel name, or only the workspace/organization name? Without channel-level information, how will chat data be fetched into the database?
   Response: The connection flow only asks for the workspace/organization name (e.g., entering “Microsoft” resolves to microsoft.slack.someapp.net). It does not ask for a channel name at this stage. The next screen is an authentication page requiring admin credentials. Once admin credentials are entered, that admin account gains the ability to install the bot into the Slack App Store/workspace. This authentication step exists purely to authorize installation — a user without admin-level access cannot install the bot at all.
   Q2: Should data fetching begin during authentication/installation itself, or only after the bot has been fully installed?
   Response: Data fetching should not happen during authentication or installation. It should begin only after the user is logged into Slack and the agent/bot has been successfully installed. Once the bot is launched, the system should then present a screen allowing the user to connect to additional platforms (Atlassian, SharePoint, G Suite, etc.), and fetching starts from that point onward.
   Q3: Should the data be structured as intents deployed on AWS Lex, or handled as a knowledge-based LLM retrieval system?
   Response: There are two categories of intents to support: (1) Global/default intents — InnovyQ’s (Ivvy Bot) existing generic intents, images, and knowledge articles, which activate immediately after Slack installation and authentication, with no dependency on other connected sources; and (2) Tenant-specific/custom intents — created against a separate tenant ID (already implemented at install time) when a customer connects additional sources such as Atlassian. These tenant-specific intents override the global ones for that customer. If no additional sources are connected, the bot should function as a generic bot using the default global intents, pictures, and knowledge repositories  of Ivvy BOT— this is expected to be sufficient for some organizations. A cost/subscription model (how many generic Q&A interactions are free before requiring a paid plan) will be defined later; for now, the priority is ensuring the global intents work correctly right after installation and authentication in Slack Workspace.
   Q4: Should a separate “data fetching” button be added for Slack, similar to how the flow currently waits on the Atlassian/Confluence connection?
   Response: No separate fetch trigger is required. Once a source such as Atlassian is connected, IvvY BOTdoes not need to manually pull data — Atlassian will push data to the backend on its own. Once admin credentials are added, InnovYQ has backend access and will continuously fetch and convert incoming queries into tenant-specific intents. This continuous fetch/convert pipeline is a follow-up backend task to be worked on at a later point.
   Q5: Specifically for Slack (as opposed to the Atlassian or SharePoint options), should the admin's Slack conversation history be fetched via a custom tile, or through some other visible mechanism?
   Response: The fetching of Slack conversation history should NOT be made visible to the customer — users should not see what data is being pulled. Instead, a backend script should execute automatically once the admin is logged in: a backend trigger fetches their chats automatically, functioning like a local/enterprise-specific LLM for that organization. No customer-facing tile or manual trigger should be used for this.

1. Meeting Summary

2. Karan's Questions & Akshat's Recommendations
   Q1. For the first-time user flow, the bot is auto-added to the initial Slack workspace. If an admin wants to add the bot to a different (additional) workspace, should the "Add to Slack" button be kept for that, or removed?
   Akshat's Recommendation: Keep the design simple. Most organizations operate on a single workspace; where multiple workspaces exist, the user can add the bot separately from that other workspace itself rather than through a manual entry mechanism. Do not add a free-text "enter workspace name" field — this would let a user unintentionally connect to a workspace they are not authenticated against (e.g., accidentally linking to a production environment while only authorized for a sandbox/non-prod one), which is a security risk. The system should simply connect to whichever workspace the user is already logged into. This capability can be hidden for now and revisited later only if customer feedback specifically calls for it — it is not difficult to add later.
   Q2. If an error occurs partway through connecting the bot to the admin's workspace (e.g., after authentication but before the tenant record is fully created), how should the admin be able to retry adding the bot, especially if the "Add to Slack" button is no longer shown at that point?
   Akshat's Recommendation: Treat onboarding as a multi-step operation (authenticate → retrieve Slack info → add bot → create tenant ID/credentials in the database → any subsequent provisioning such as intents). Every step is a potential point of failure. Each step should be retried automatically a few times (e.g., once a minute); if it still fails after 3 retries, the whole operation should be marked failed and all completed steps for that tenant rolled back (cleanup), rather than left in a partial state. The user should then see a simple, elegant error message asking them to retry after some time — similar to how a standard "Sign in with Google" flow behaves if its background steps fail: no attempt is made to resume from the exact failure point. Karan raised a concern that asking the user to restart the entire flow (including re-entering credentials) feels laborious; Akshat's counter-point was that without a completed tenant record, the system has no reference to resume against, and that keeping the workflow simple (fail-and-retry) avoids the complexity of handling many partial-failure scenarios as the product scales across connectors and customers.
   Q3. When answering user queries from the data retrieved via Slack, should the bot use an LLM-based approach, or an intent-based approach (creating intents and deploying via AWS, which adds latency)? Is this decision part of the initial bot/onboarding setup?
   Akshat's Recommendation: This is a separate concern from the onboarding workflow and does not need to be decided as part of it. Onboarding is purely about provisioning a tenant — comparable to filling out a signup form and creating an account (e.g., Gmail account creation) — and has nothing to do with how conversations or queries are later handled. During onboarding, the system will populate database tables, generate a tenant ID, and — only if required — pre-populate supporting infrastructure such as global or tenant-specific intents. Separately, whether historical Slack conversation data should be pulled in and stored for a tenant is an open question with privacy implications; if needed, it can be fetched in the background and stored, but it is not a mandatory part of onboarding.
   Q4. Should the workflow allow an admin to grant multiple users admin-level access (to install/manage the bot)?
   Akshat's Recommendation: This is already governed by Slack's native admin/permission system and does not need to be built by the bot. Whoever has Slack admin rights within the organization will see the install option; that access is determined entirely by the customer's own Slack workspace settings, not by the bot. Once the bot is installed, it should be visible and usable by all users in that workspace by default — no separate access-control layer is needed for now.
3. Additional Recommendations from Akshat
   •	Build retry-and-rollback resiliency into every step of the onboarding workflow: on failure, retry every minute; after 3 failed retries, fail the step and roll back the tenant's prior steps. Keep this logic "under the hood" — the UI should simply show a loading/spinner state while these operations run in the background.
   •	Maintain a database-driven active/inactive status check for each customer/tenant. If a customer's status is inactive (e.g., expired plan), block the request and surface a clear, meaningful message in the UI rather than silently failing.
   •	For bot visibility/access within a workspace, avoid building granular per-user access controls for now. Default behavior: once installed, the bot is available to all workspace users. Build selective access only if a specific customer use case demonstrates the need — otherwise it is unnecessary over-engineering.
   •	Current focus should remain on building and polishing the onboarding flow end-to-end, including the existing Slack authorization button and the failure-handling behavior discussed above.
   •	Akshaya's frontend work was reviewed briefly; no material changes since the version shown the previous day.
4. Decisions Made
   •	The manual "enter workspace name" / multi-workspace-entry option will not be built at this stage; the bot will connect only to the Slack workspace the authenticated user is currently logged into.
   •	Onboarding failures will use a simple retry-then-rollback model (3 retries) rather than attempting to resume from the exact point of failure.
   •	Bot access within a workspace will default to "available to all users" once installed; no per-user permission layer will be built initially.
