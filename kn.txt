The worker Lambda does not directly call IAM.
It calls EventBridge Scheduler, and passes the IAM role ARN inside the schedule request.
In code:
SCHEDULER_ROLE_ARN = os.environ.get("SCHEDULER_ROLE_ARN")
This reads the role ARN from Lambda env vars. Then the worker uses it here: [lambda_o3_slack_worker.py (line 128)](/E:/Project IVY/lambda_o3_slack_worker.py:128)
"Target": {
    "Arn": TIMEOUT_HANDLER_ARN,
    "RoleArn": SCHEDULER_ROLE_ARN,
    "Input": json.dumps(payload)
}
Meaning:
EventBridge Scheduler, later invoke TIMEOUT_HANDLER_ARN.
When you invoke it, assume/use SCHEDULER_ROLE_ARN.
Worker Code Flow
Worker receives an SQS message in process_record: [lambda_o3_slack_worker.py (line 262)](/E:/Project IVY/lambda_o3_slack_worker.py:262)

Worker calls Lex and gets a reply.

If conversation is still active, worker creates timeout data:

timeout_due_at = now + 15 minutes
timeout_token = unique safety token
timeout_schedule_name = deterministic schedule name
This starts around [lambda_o3_slack_worker.py (line 316)](/E:/Project IVY/lambda_o3_slack_worker.py:316).
Worker stores timeout fields in DynamoDB: [lambda_o3_slack_worker.py (line 401)](/E:/Project IVY/lambda_o3_slack_worker.py:401)

Worker calls refresh_timeout_schedule: [lambda_o3_slack_worker.py (line 157)](/E:/Project IVY/lambda_o3_slack_worker.py:157)

refresh_timeout_schedule calls upsert_schedule.

upsert_schedule calls AWS EventBridge Scheduler:

scheduler.update_schedule(...)
or:
scheduler.create_schedule(...)
See [lambda_o3_slack_worker.py (line 146)](/E:/Project IVY/lambda_o3_slack_worker.py:146).
What IAM Does Here
When worker calls create_schedule, AWS checks:
Is the worker Lambda execution role allowed to create schedules?
Is it allowed to pass SCHEDULER_ROLE_ARN?
So the worker Lambda execution role needs:
scheduler:CreateSchedule
scheduler:UpdateSchedule
scheduler:DeleteSchedule
iam:PassRole
Then later, EventBridge Scheduler uses SCHEDULER_ROLE_ARN to invoke the timeout handler Lambda.
Timeout Execution Flow
After 15 minutes:
EventBridge Scheduler -> invokes timeout handler Lambda
Timeout handler entry point: [lambda_o3_slack_timeout_handler.py (line 470)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:470)
Then:
lambda_handler receives event with action="prompt".
It calls handle_prompt: [lambda_o3_slack_timeout_handler.py (line 350)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:350)
It reads DynamoDB and checks timeout_token.
If token is still current, it sends Slack timeout prompt.
Then it schedules itself again for the close action using schedule_close: [lambda_o3_slack_timeout_handler.py (line 129)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:129)
After 5 more minutes:
EventBridge Scheduler -> invokes timeout handler again with action="close"
Then handle_close marks the session closed: [lambda_o3_slack_timeout_handler.py (line 412)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:412)
Key point: worker does not “execute timeout” itself. It creates a future schedule. EventBridge Scheduler executes the timeout later by invoking the timeout handler.

Left menu → Bot versions.
Click Create version.
Select the built Draft locale: English (US).
Add description, for example:
Loaded 21 IVY support intents from Intents_20_List.xlsx
Click Create.
You will get something like:
Version 3
Step 2: Update Existing prod Alias
Left menu → Aliases.
Click prod.
Click Edit.
Find Associated version.
Change it from:
Version 2
to:
Version 3
Save.
Now Slack will use the new intents if your worker Lambda BOT_ALIAS_ID points to the prod alias ID.
Step 3: Check Worker Lambda
Open Lambda.
Open o3-slack-worker.
Go to Configuration → Environment variables.
Check:
BOT_ALIAS_ID
If that alias ID is the prod alias ID, you are done.

You are working on my AWS Lambda Slack bot project. Refactor the session closing and summarization flow.


Main goal:
Build a clean and reliable session closing flow for:
- 1-to-1 Slack DMs
- Group DMs / multi-person DMs


Core Slack behavior:
Do not decide whether something is a DM or channel only from the channel ID prefix.

The bot must detect the Slack conversation type using Slack conversation metadata.

Conversation behavior:
- 1-to-1 DM: send normal DM messages, not thread replies.
- Group DM / multi-person DM: send normal group DM messages, not thread replies.


Important reason:
A group DM can appear under “Direct messages” in Slack but may technically look like a private conversation/channel internally. So the bot must detect the actual conversation type before deciding whether to use thread replies.

Close button display rule:
The “Close & summarize” button should not appear immediately for simple greetings or test messages such as:
- hi
- hello
- hey
- good morning
- test

Show the “Close & summarize” button only after:
- the user has described a real issue,
- the bot has given a meaningful answer, troubleshooting step, or resolution suggestion,
- and the session is active and waiting for the user.

Do not show the close button when:
- the conversation is only a greeting,
- the bot is still collecting required details,
- the session is already summarizing,
- the session is already closed,
- or the session has failed.

After every meaningful bot answer, show two user actions:
- Close & summarize
- I need more help

Button behavior:
In 1-to-1 DMs and group DMs:
- Show the button as a normal message.
- Do not create a Slack thread reply.


Recommended session states:
- OPEN
- COLLECTING_DETAILS
- WAITING_FOR_USER
- SUMMARIZING
- CLOSED
- FAILED

Normal conversation flow:
1. User sends a message.
2. Bot creates or updates the session in DynamoDB.
3. Bot determines whether the user has described a real issue.
4. If more details are needed, bot asks follow-up questions.
5. If enough information is available, bot gives a useful answer or troubleshooting step.
6. After a meaningful answer, the session moves to WAITING_FOR_USER.
7. Bot shows the “Close & summarize” and “I need more help” actions.
8. User can continue chatting, ask for more help, close the session, or leave it inactive until timeout.

Close and summarize flow:
1. Close event is received.
2. Bot validates the event and required configuration.
3. Bot detects the Slack conversation type.
4. Bot checks the DynamoDB session state.
5. If the session is already summarizing or closed, do not run the close flow again.
6. If the session is valid and active, mark it as SUMMARIZING.
7. Remove or disable the close button if possible to prevent duplicate clicks.
8. Collect the conversation.
9. Clean the conversation.
10. Send the cleaned conversation to Power Automate.
11. Save the raw audit log to S3.
12. Send a useful final closed message to Slack.
13. Send the feedback rating prompt.
14. Mark the DynamoDB session as CLOSED.
15. Delete the related EventBridge Scheduler timeout.


For 1-to-1 DMs and group DMs:
- Do not depend on Slack thread replies because DM/group DM messages should not be posted in threads.
- Use the session messages stored in DynamoDB during the active conversation.
- Store meaningful user and bot messages during the active session so they are available for summarization later.

Conversation cleaning rules:
Remove system, timeout, close, and feedback messages such as:
- inactivity warnings,
- summarizing/closing notices,
- no-response messages,
- final closed messages,
- feedback prompts.

Preserve meaningful user and bot messages.

The cleaned conversation should clearly distinguish:
- User messages
- Bot messages

The summary should be based only on meaningful conversation content.

Power Automate payload requirements:
Send the cleaned conversation, user information if available, channel information, thread/session information, conversation type, close reason, and any raw audit context needed for follow-up or Jira integration.

If Power Automate returns a structured summary, use that summary in the final Slack message.

Final Slack message behavior:
If a summary is available, send a message like:

✅ This session is now closed.

Summary:
• Issue: ...
• Resolution: ...
• Next step: ...

Saved successfully for follow-up.

If no structured summary is returned but logging succeeds, send:

✅ This session is now closed.

Summary saved successfully for follow-up.

Feedback prompt:
After the final close message, send a star-rating prompt:
- 1 star
- 2 stars
- 3 stars
- 4 stars
- 5 stars

Feedback prompt behavior:
- In 1-to-1 DMs and group DMs, send it as a normal message.


Failure behavior:
Do not mark the session as CLOSED before Power Automate and S3 audit logging succeed.

If Power Automate or S3 fails:
- Mark the session as FAILED.
- Keep the session not fully closed.
- Store the error message in DynamoDB.
- Notify the user that the summary/save step could not be completed.
- Avoid silently closing the session when the summary was not saved.

Duplicate close prevention:
If the user clicks “Close & summarize” more than once:
- Do not run the summarization flow multiple times.
- If the session is already summarizing, tell the user it is already being closed.
- If the session is already closed, tell the user it has already been closed.

Timeout behavior:
If the user does not respond for the configured timeout period:
- Trigger the same close-and-summarize flow.
- Use a close reason indicating inactivity or no response.
- Follow the same summarization, audit logging, final message, feedback, and cleanup process.

Scheduler cleanup:
After successful close, delete the related EventBridge Scheduler timeout.
If the schedule is already deleted or missing, ignore that safely.
Log unexpected scheduler cleanup errors.

Security and logging:
- Do not log Slack tokens.
- Do not log Power Automate webhook URLs.
- Do not log secrets.
- Avoid logging full raw Slack history in CloudWatch unless needed for debugging.
- Store full raw audit data in S3 instead.
- Log only useful operational information such as session ID, channel type, state transition, and success/failure status.

Expected output:
Refactor the Lambda into clean production-friendly code.
Keep the implementation readable and modular.
Make the close-and-summarize behavior reliable for:
- 1-to-1 DM
- group DM / multi-person DM


Most important rule:
DM and group DM should not use Slack thread replies.

Most important flow:
Show “Close & summarize” only after a meaningful answer.
For DMs and group DMs, summarize from stored session messages.
Save the summary and audit log before marking the session CLOSED.
