The worker Lambda does not directly call IAM.
It calls EventBridge Scheduler, and passes the IAM role ARN inside the schedule request.
In code:
SCHEDULER_ROLE_ARN = os.environ.get("SCHEDULER_ROLE_ARN")
This reads the role ARN from Lambda env vars. Then the worker uses it here: [lambda_o3_slack_worker.py (line 128)](/E:/Project IVY/lambda_o3_slack_worker.py:128)
"Target": {
    "Arn": TIMEOUT_HANDLER_ARN,
    "RoleArn": SCHEDULER_ROLE_ARN,
    "Input": json.dumps(payload)
}
Meaning:
EventBridge Scheduler, later invoke TIMEOUT_HANDLER_ARN.
When you invoke it, assume/use SCHEDULER_ROLE_ARN.
Worker Code Flow
Worker receives an SQS message in process_record: [lambda_o3_slack_worker.py (line 262)](/E:/Project IVY/lambda_o3_slack_worker.py:262)

Worker calls Lex and gets a reply.

If conversation is still active, worker creates timeout data:

timeout_due_at = now + 15 minutes
timeout_token = unique safety token
timeout_schedule_name = deterministic schedule name
This starts around [lambda_o3_slack_worker.py (line 316)](/E:/Project IVY/lambda_o3_slack_worker.py:316).
Worker stores timeout fields in DynamoDB: [lambda_o3_slack_worker.py (line 401)](/E:/Project IVY/lambda_o3_slack_worker.py:401)

Worker calls refresh_timeout_schedule: [lambda_o3_slack_worker.py (line 157)](/E:/Project IVY/lambda_o3_slack_worker.py:157)

refresh_timeout_schedule calls upsert_schedule.

upsert_schedule calls AWS EventBridge Scheduler:

scheduler.update_schedule(...)
or:
scheduler.create_schedule(...)
See [lambda_o3_slack_worker.py (line 146)](/E:/Project IVY/lambda_o3_slack_worker.py:146).
What IAM Does Here
When worker calls create_schedule, AWS checks:
Is the worker Lambda execution role allowed to create schedules?
Is it allowed to pass SCHEDULER_ROLE_ARN?
So the worker Lambda execution role needs:
scheduler:CreateSchedule
scheduler:UpdateSchedule
scheduler:DeleteSchedule
iam:PassRole
Then later, EventBridge Scheduler uses SCHEDULER_ROLE_ARN to invoke the timeout handler Lambda.
Timeout Execution Flow
After 15 minutes:
EventBridge Scheduler -> invokes timeout handler Lambda
Timeout handler entry point: [lambda_o3_slack_timeout_handler.py (line 470)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:470)
Then:
lambda_handler receives event with action="prompt".
It calls handle_prompt: [lambda_o3_slack_timeout_handler.py (line 350)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:350)
It reads DynamoDB and checks timeout_token.
If token is still current, it sends Slack timeout prompt.
Then it schedules itself again for the close action using schedule_close: [lambda_o3_slack_timeout_handler.py (line 129)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:129)
After 5 more minutes:
EventBridge Scheduler -> invokes timeout handler again with action="close"
Then handle_close marks the session closed: [lambda_o3_slack_timeout_handler.py (line 412)](/E:/Project IVY/lambda_o3_slack_timeout_handler.py:412)
Key point: worker does not “execute timeout” itself. It creates a future schedule. EventBridge Scheduler executes the timeout later by invoking the timeout handler.

Sir,
I wanted to share a quick update on the features implemented so far in the O3 Bot, along with the remaining items planned for the next phase.
The following capabilities have been implemented till now:
Slack Integration







O3 Bot can receive and respond to user messages from Slack.


Supports Slack DM and thread-based conversations.


Slack events are routed through API Gateway, Lambda, SQS, and worker Lambda.

Event Processing Pipeline







Slack events are processed asynchronously using SQS.


Dead-letter queue support is configured for failed messages.


Duplicate Slack event handling has been implemented using DynamoDB.

Session Management







User sessions are stored and tracked in DynamoDB.


Session state includes Slack channel, user, thread, last user message, bot response, Lex state, Jira ticket state, and live-agent status.


DM-based and thread-based conversation handling is supported.

Amazon Lex Integration






O3 Bot is integrated with Amazon Lex for intent detection.


Lex handles structured conversational flows before escalation.

Claude / Bedrock AI Fallback






Claude fallback support has been added for unresolved cases.


The bot can provide AI-generated assistance before offering escalation options.

Support Options Flow





Users can choose next actions such as:








Continue with AI assistance


Create Jira ticket


Request live-agent support


Close and summarize conversation

Jira Ticket Creation








Jira ticket creation flow is implemented.


Duplicate ticket creation prevention and lock handling are in place.


Slack confirmation is sent after ticket creation.


Jira ticket metadata is stored in DynamoDB.

Live Agent Handoff







Users can request live-agent support from Slack.


Live-agent requests are created in the IVY Live Agent Support JSM project.


Slack user details, channel, thread, session ID, and conversation summary are passed to JSM.

JSM Ticket Created Callback







JSM automation sends ticket creation details back to AWS.


O3 Bot stores live-agent ticket mapping in DynamoDB using records such as live_agent_ticket:IVY-xx.


Slack receives confirmation with the created JSM ticket key.

JSM Status Updates to Slack


Status changes in JSM are synced back to Slack.


Supported updates include:








In Progress


Waiting for Customer


Waiting for Support


Resolved


When a ticket is resolved, the related Slack session is closed in DynamoDB.

JSM Agent Reply to Slack


When an agent uses “Reply to customer” in JSM, the message is sent back to the original Slack conversation.


Echo-loop prevention has been added to avoid duplicate Slack/JSM message loops.

Slack User Reply to JSM


Worker logic has been implemented to route Slack user replies back to the same JSM ticket as comments.


Current work is focused on ensuring JSM tickets are created with the correct Request Type so comments are customer-visible.

Reliability and Idempotency


Duplicate callbacks are prevented using DynamoDB marker records.


Duplicate Slack retries are handled.


Ticket creation, status update, and comment callbacks have idempotency safeguards.

CloudWatch Logging


JSON-based logging has been added for easier debugging.


Logs include session ID, ticket key, callback type, status, and error codes.
